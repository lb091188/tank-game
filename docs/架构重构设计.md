# 架构重构设计：模拟核心共用 + 计算全面入工作线程

> 状态：**待评审** —— 本文是动代码前的设计定稿，评审通过后按阶段实施。
> 目标（需求原话）：坦克的机制逻辑服务端和客户端共用；客户端主线程只负责渲染；服务端主线程只负责通信；所有的计算逻辑放工作线程。

## 1. 现状与差距

| 维度 | 现状 | 目标 | 差距 |
|---|---|---|---|
| 战斗模拟 | 客户端**主线程**（vehicle.js 436 行 + combat.js 296 行 + main.js 游戏循环） | 工作线程 | 模拟核心与 THREE 网格耦合 |
| 命中判定 | 主线程 raycast 坦克 **GLB 部位网格**（combat.js `ray.intersectObjects(tk.parts.zones)`） | worker/Node 可用 | THREE 依赖，worker 无 THREE |
| AI 决策 | ✅ 已在 worker（ai-worker.js），但靠 10Hz 快照维护"副本世界" | 与模拟同线程直读 | 需合并 |
| 点亮/隐蔽 | 主线程（main.js）+ simcore 纯函数 | 模拟核心内 | 移动 |
| 联机模型 | **主机权威**：房主浏览器跑权威模拟并广播，Node 服务器纯转发 | 服务器权威：服务器 worker 跑模拟 | 协议与信任模型变更 |
| 共用逻辑 | simcore.js（地形/掩体/隐蔽，主线程与 worker 共用，零 THREE） | 全部机制逻辑共用 | 扩展成完整 sim-engine |

隐藏大坑（现状代码）：随机数大量使用 `Math.random()`（散布/穿深浮动/伤害浮动/AI 性格）。快照同步模型下无碍；若未来考虑锁步或严格确定性回放，必须先换成注入种子的 PRNG（mulberry32 已在 build-map.js 用过）。本设计采用**快照同步**，不做锁步，规避此坑。

## 2. 目标架构

```
┌─ 浏览器 ──────────────────────────────┐   ┌─ Node 服务器 ─────────────────────┐
│ 主线程(渲染)        sim-worker         │   │ 主线程(WS/房间/钥匙)   每房间worker  │
│ ┌──────────┐   init/输入30Hz  ┌─────┐ │   │ ┌──────┐  输入30Hz   ┌──────────┐ │
│ │ 渲染/特效 │ ◄──快照20-30Hz── │ sim │ │   │ │ 房间 │ ◄──────────► │ sim-     │ │
│ │ 音频/HUD  │ ◄──事件流─────── │ eng │ │   │ │ 路由 │ ──快照20Hz──► engine    │ │
│ └──────────┘                  │ +AI │ │   │ └──────┘              │ (+coopAI)│ │
│          单机: 同一 worker,无网络      │   └───────────────────────└──────────┘ │
└──────────────────────────────────────┘   └────────────────────────────────────┘
                    ▲________ sim-engine.js（同一份文件）________▲
                    零 THREE / 零 DOM / 零 Node API；window/self/worker_threads 通吃
```

单机、联机主机、联机客户端**跑同一条客户端路径**（本地 worker 或连服务器），消灭现在 sp/host/client 三分叉的重复模拟代码。

## 3. 模块设计

### 3.1 sim-engine.js（纯模拟核心，阶段 1 产出）

从现有代码平移，去 THREE 化：

| 内容 | 来源 | 改造点 |
|---|---|---|
| 行驶/自动挡/转向/车车碰撞/掩体碰撞/地形贴合/**坠落摔伤** | vehicle.js `update()` | 输出纯数值状态 `{x,z,y,yaw,pitch,roll,turretYaw,gunPitch,gear,speed,hp,modules…}`；表现同步（网格位姿）留在主线程渲染侧 |
| 炮塔/火炮瞄准约束（射界/俯仰/回转限速） | vehicle.js 瞄准段 | 同上 |
| 开炮（散布锥/弹夹/装填） | vehicle.js `fire()` | `Math.random()` → 注入 PRNG（每局一个种子，快照里带结果事件） |
| 弹道积分/地形/掩体命中 | combat.js | 向量改普通对象；THREE.Vector3 全部换 `{x,y,z}` + 自写运算 |
| **坦克命中判定** | combat.js raycast GLB | **改部位 OBB 盒**（见 3.2） |
| 装甲判定/模块损毁/溅射/撞击 | vehicle.js takeHit 等 | normal/point 去 THREE 化 |
| 点亮/隐蔽/残留 | main.js spotted 段 + simcore | 周期 0.25s 不变，输出 spotted 集合 |
| 地形/掩体场 | simcore.js（已是纯的） | 原样并入 |
| AI | ai.js（已是纯的，依赖注入 world 接口） | 直读 engine 状态，删除副本世界/快照复制 |

对外接口（草案）：

```js
SimEngine.create({ mapJson, heights, covers, players: [{tankSpec, spawn, isAI…}], seed })
  → { step(input[], dt)            // 60Hz 定步长
      snapshot()                    // 全量/增量快照(位姿/血量/装填/点亮/弹着)
      drainEvents()                 // 开炮/命中/摧毁/断带/点亮变化…(替代 SF.Bus)
      applyInput(playerId, input) } // 输入注入(服务器侧做合法性 clamp)
```

### 3.2 命中判定：GLB 网格 raycast → 部位 OBB

- **数据**：tools/build-models.js 构建每车时，导出部位盒表 `{zone, armor, cx,cy,cz, hx,hy,hz, yaw,pitch }`（相对车体/炮塔局部系），随模型一起进 config；部位沿用现有 zone 语义（hullFront/Side/Rear/Top、turret、gun、track…）。
- **判定**：线段 vs OBB——`Util.rayObb` 已存在（simcore 掩体判定同款），命中取最近盒、面法线做入射角；炮塔盒挂在炮塔局部系随 turretYaw 转。
- **精度取舍**：弧形炮盾/复杂外形由 2~3 个盒拼合；WoT 本身也是可视化模型的简化碰撞体。评审点：**跳弹手感会略有变化**，需盲测 + 命中/击穿率统计对比（现版本先跑基线数据）。
- 兜底：hitbox 精度不够时，部位盒可离线从 GLB 自动包络生成（扫网格顶点求各 zone 的 OBB），不手填。

### 3.3 客户端 sim-worker（阶段 2）

- 照 ai-worker 模式：Blob worker + `importScripts(BASE + 'sim-engine.js')`。
- 消息协议：`init`（地图高程/掩体表/车辆配置，复用现有 transfer）｜`input`（主线程 30Hz 上报键鼠/瞄准）｜`snap`（worker 20-30Hz 下发）｜`ev`（事件流，主线程翻译成特效/音频/HUD/SF.Bus）。
- 渲染侧：复用现联机插值 `Net.interpolate(120ms)`；单机也走同一缓冲（消除单机/联机手感差异）。
- AI 并入该 worker，删除 ai-worker.js 与 10Hz 快照复制、`_aiSeen` 回传链路。

### 3.4 服务端权威（阶段 3）

- server.js 主线程只做：WS/房间/钥匙门禁/战绩落盘（现状保留）+ 每房间 `new Worker('sim-server.js')`。
- sim-server.js：`require('./sim-engine.js')`（CommonJS 包装），每房间一线程，收输入、跑 60Hz、广播 20Hz 快照；coop 的 AI 在此线程跑（**房主掉线不再灭队**）。
- 协议变更（破坏性）：`host` 广播快照的角色由服务器接管；客户端只剩"发输入 + 渲染快照"。协议版本号门禁，旧客户端给出升级提示；`tools/steel-ws-test.js` 回归用例重写（31 项 → 覆盖服务器权威路径）。
- 基础反作弊：输入频率/幅度 clamp（油门∈[-1,1]、炮塔角速度上限）。
- 部署影响：每房间一个线程（~30-60MB），VPS 小内存需注意并发房间数；可退化单线程多房间（先不做）。

## 4. 实施顺序与验收（每阶段独立 commit，可回滚）

| 阶段 | 内容 | 验收标准 | 预估改动量 |
|---|---|---|---|
| 0 | 事件总线抽象（SF.Bus 可替换后端）；Tank 数值状态与网格表现分离 | 行为零变化；31 项协议回归通过 | ~400 行 |
| 1 | sim-engine 提取 + OBB 命中（仍跑主线程） | 命中/击穿率与基线偏差 <3%（自动化对局统计）；手感盲测 | ~1500 行 |
| 2 | 客户端模拟入 worker + AI 合并 | 主线程单帧脚本时间下降（F3 角标对比）；单机=联机路径 | ~800 行 |
| 3 | 服务端权威 + 协议重写 + 回归重建 | 服务器杀房主进程对局继续；新回归全绿 | ~1000 行 |

## 5. 明确不做

- **锁步同步（lockstep）**：延迟敏感、调试成本高，快照模型已满足；也回避了跨端浮点/随机的严格确定性问题。
- 输入回滚（rollback netcode）：坦克游戏节奏不需要。

## 6. 风险清单

1. 命中手感变化（3.2）→ 基线对比 + 盒精度可调 + 自动包络兜底。
2. worker 消息序列化开销（快照 20Hz × 8 车位姿 ≈ 2KB/s，可忽略；事件流突发可控）。
3. 阶段 3 协议不兼容 → 版本门禁；联机是内网/自建服场景，强制升级可接受。
4. 主线程现在依赖模拟结果的即时性（准星/瞄准反馈）→ 输入本地预测只做炮塔指向，其余走插值。
5. `Math.random()` 散布：快照模型下两端各算各的、以模拟端为准，无需先统一；但阶段 3 服务器跑弹道时散布在服务器侧掷点，天然权威。
